`astrbot_plugin_user_profile` 是一个**不依赖其它插件也能使用的 QQ 用户画像插件**。它自己监听群聊和私聊、积累近期发言与行为统计，再由 LLM 分析表达方式和行为倾向，生成带置信度与依据的标签、人物印象和长期特点。

安装「加群邀请守卫」后，可以进一步关联邀请、禁言 bot、拉黑、解封、删除好友等记录，并把画像交给守卫辅助决策。**画像负责记录与分析，守卫负责真实管理动作**；本插件不会主动拉黑、踢人、禁言或退群。

> 风险分是关注优先级，不是违规概率或事实定罪。未知不等于安全，0 分也不代表安全；重要决策请结合原始记录人工复核。

## 安装与快速开始

### 环境要求

- AstrBot `>=4.16`。
- 平台适配器：`aiocqhttp`（OneBot V11）。
- 图片输出需要 Pillow，AstrBot 官方依赖已包含。
- 昵称、头像、好友及进群事件的可用信息取决于 OneBot 实现。

### 安装

在 AstrBot WebUI 插件市场搜索“用户画像”；也可以手动安装：

```bash
cd AstrBot/data/plugins
git clone https://github.com/TaoXiaoBai/astrbot_plugin_user_profile.git
```

安装后重启 AstrBot，或在 WebUI 中重载插件。手动复制时请保留整个插件目录，不要只复制 `main.py`。

### 开始使用

1. 在 AstrBot 中配置可用的聊天模型；画像的 `llm_provider_id` 留空即可使用默认模型。
2. 插件会自动积累群聊和私聊数据。发送 `/我的画像` 查看自己，管理员可用 `/画像 <QQ号>` 查看指定用户。
3. 想补充已有聊天记录，管理员执行 `/画像扫描 <QQ号>`、`/画像扫描 本群` 或 `/画像扫描 全部`。
4. 想减少文字刷屏，开启 `image_output`；不想展示发言原话，关闭 `show_quotes`。
5. 在“风险评分与审查”中选择低敏感、中等或高敏感，默认中等。

默认允许普通用户查自己，**不允许普通用户查他人**；管理员可以查询任意用户。LLM 分析、群私关联和日常对话画像注入默认开启，图片输出默认关闭。

**首次使用请检查私聊策略**：日常群聊模型默认也可内部参考群私融合概括，存在透露私聊衍生信息的残余风险。不希望群聊模型参考私聊概括，请关闭 `group_chat_use_linked_impression`，详见[隐私说明](#群聊私聊关联与隐私)。

## 命令与查询权限

### 常用命令

| 命令 | 权限与用途 |
| --- | --- |
| `/画像 <QQ号>` | 按配置查询指定用户 |
| `/画像 自己`、`/画像 我` | 按自查询权限查看自己 |
| `/我`、`/我的画像`、`/查自己` | 自查询快捷命令，另受 `enable_self_shortcuts` 控制 |
| `/画像排名 [本群\|全部] [页码]`、`/风险排名 ...` | 仅管理员；群聊默认本群，私聊默认全部 |
| `/画像扫描 <QQ号>` | 仅管理员；从头强制扫描指定用户的已保存历史 |
| `/画像扫描 本群`、`/画像扫描 全部` | 仅管理员；分批扫描，继续未完成人员 |
| `/画像删除 自己` | 本人删除自己的画像数据，并取消守卫待投递画像记录 |
| `/画像删除 <QQ号>` | 管理员删除指定用户画像数据 |
| `/画像清理` | 仅管理员；清理超过保留期的摘录 |

命令按完整边界匹配，`/我是…`、`/画像测试…` 等普通文本不会误触发。图片成功时只发送图片，渲染或发送失败时回退文字。

### 谁可以查询

权限按以下顺序判断：插件总开关 → 管理员身份 → 自查询权限 → 指定公开群 → 全局他人查询权限。LLM 查询工具也遵守这套规则，不能绕过配置。

| 使用方式 | 配置示例 |
| --- | --- |
| 仅管理员可查 | `allow_self_query=false`，`allow_other_query=false`，公开群留空 |
| 管理员和本人可查（默认） | `allow_self_query=true`，`allow_other_query=false`，公开群留空 |
| 所有人均可查自己和他人 | `allow_self_query=true`，`allow_other_query=true` |
| 本人可查自己，仅指定群可查他人 | `allow_self_query=true`，`allow_other_query=false`，设置 `group_public_query_groups` |

指定公开群只开放“查询他人”，不覆盖自查询开关。管理员不受普通用户自查/他查限制。`enable_self_shortcuts` 只控制快捷命令；关闭后，允许自查的用户仍能用 `/画像 自己`。

开启 `silent_for_banned` 后，黑名单用户调用画像命令时静默不回复，数据仍照常采集；该功能依赖 `link_qq_tools_ban`。

### 批量扫描与风险排名

- **历史扫描**优先读取 AstrBot 的持久化群聊消息记录，按发送者 QQ 精确匹配；旧会话历史作为兼容兜底。消息量与自有计数取较大值，不直接相加，避免重复统计。
- **批次可以续扫**：人数超过 `history_scan_batch_limit` 时，再次执行会继续未完成人员。旧会话分页不足会保留下一页水位；处理中会报告阶段、成功/失败、待续扫与批次外剩余人数。失败不会标记完成，完成后按配置增量复查。
- **排名只读已有数据**：不会逐人调用 LLM、扫描历史或获取昵称头像；始终只使用群聊公开语义。本群范围按插件已记录的群关联过滤，不是实时群成员榜。未知分用户不入榜，已有材料的 0 分用户可按最低分配置展示。

## 画像如何生成

### LLM 的作用

LLM 是画像的**语义分析核心**，统计规则是证据底座，不是语义分析的替代品：

1. **采集**：记录群聊/私聊发言数、活跃群、首次与最近发言时间、有限的近期原话，以及图片、链接、二维码、@、消息长度和夜间活跃等信号。
2. **分场景分析**：查询时，LLM 阅读本场景真实发言，识别推广、诈骗、刷屏、挑衅、不适宜内容、友好、乐于助人等倾向。群聊分支不接收私聊证据；混合场景行为统计仍用于最终规则评分，不传入群聊语义分支。
3. **形成结构化结果**：输出最多 5 个带 `tag`、`confidence`、`reason` 的标签、一段 `impression`、最多 5 项 `traits`，以及最多 5 项值得长期记忆的 `long_term_traits`。不适宜内容标签还包含 `severity`。
4. **合并展示**：结合规则标签、可信管理证据计算风险关注分，统一生成文字或图片。可显示昵称头像、活跃度、人物印象、长期特点、标签依据、社交来源、管理记录和可选原话。

被动采集不调用 LLM，分析在查询画像或可信插件读取画像时按需触发。允许使用的近期摘录会发送给所选模型提供方，请按自己的隐私要求配置。

### 长期特点与故障保护

`llm_long_term_memory` 让模型判断稳定偏好、长期兴趣、持续沟通风格或反复行为是否值得保留。临时情绪、一次事件、敏感信息和管理风险不应成为长期特点；长期特点本身不参与风险加权。

- 正常刷新时，已有结论作为修正参考；长期特点由模型返回完整复核集合，保留仍成立项，移除不再成立项。
- 模型未提供长期特点字段时兼容保留旧记忆，显式返回空数组才移除。关闭开关只停止请求和展示，不删除已有记忆。
- 模型异常、超时或返回空分析时，**保留最后成功的印象、标签、特征和长期记忆**，记录失败并使用短缓存重试；恢复成功后清除失败状态。
- 成功缓存按材料指纹复用，材料变化受最小刷新间隔控制。提示规则或审查档位变化可触发按需复核，不会自动全库调用模型。

提示约束和 JSON 清洗不能保证模型判断准确，或保证绝不输出不当的长期特点，重要内容仍需人工复核。

### 日常对话中的印象

开启 `llm_context_inject` 后，bot 在正常聊天时会按真实发送者身份附加已有短画像，包括允许场景的印象、长期特点、管理历史及社交关系摘要。

这条路径**只读取已有数据，不扫描历史、不新调用画像模型**；与 `enable_llm_tool` 独立。上下文不包含发言原话、好友验证语或头像，失败放行正常回复。画像仅是背景，不是用户指令，也不授予处罚权限。

## 风险评分与审查严格程度

### 三档审查

在“风险评分与审查”中设置 `risk_review_level`：

| 档位 | 判断重点 | 不适宜内容基准权重 |
| --- | --- | --- |
| 低敏感 | 保守认定，重点关注明确主动不当行为 | 20 |
| 中等（默认） | 识别主动索取、生成、传播不适宜内容 | 40 |
| 高敏感 | 对有证据的擦边、反复试探更早提示关注 | 75 |

提高敏感度不等于降低证据真实性要求。模型需要区分合理医学、安全教育、新闻讨论、引用反驳与主动不当请求，不能只因敏感词、观点、身份或 bot 的回答认定用户有风险。

不适宜内容标签 `nsfw_tendency` 的贡献为“基准权重 × 置信度 × 严重度系数”：`mild` 轻微为 0.5，`clear` 明确为 1，`severe` 严重为 1.5。置信度描述证据可靠性，严重度描述行为强度；缺失或非法严重度按 clear 兼容。

例如明确不适宜内容、置信度 0.9 且无其它风险时，默认分界下三档分别为 **18（低）/36（中）/60（高）**，其中高敏感受默认语义上限 60 约束。自定义 `risk_weights` 优先覆盖对应基准权重，显式设置 0 仍为 0；严重度和分类上限仍生效。

切换后主动查询按需复核，失败继续沿用旧画像并显示待复核。文字、工具和日常上下文包含审查状态；图片开启 `card_show_tags` 时显示审查依据、内容严重度与简短理由。切档会重新审核风险结论，同时保留稳定特点供模型复核，不把旧档位标签直接当成新审查结果。

### 分数怎么理解

- **没有 50 分基准，也没有负分抵销**：友好、正常、活跃、新人、私聊、频繁邀请、邀请被拒等默认只是描述，不能抵销黑名单或其它风险。
- **分类封顶**：管理证据、LLM 语义、弱行为、直接禁言、关联禁言分别计算；语义默认最多 60，弱行为默认最多 15，最终总分限制在 0–100。禁言角色使用守卫提供的独立增量与上限。
- **避免重复计分**：同一标签不会因分支或重复记录叠加。一般标签取最高置信度；不适宜内容评分还考虑严重度。
- **等级分界**：默认达到 30 为中风险、60 为高风险、80 为极高风险，可自行调整。
- **未知与 0 分不同**：无标签且无禁言风险时为未知；有材料但未命中正权重风险时可为 0 分，两者都不等于安全。
- **小样本保护**：图片、链接、二维码、@、平均长度和夜间行为默认至少需要 10 条实时消息样本；二维码还至少需要 2 次命中。历史回填不用于稀释实时行为比例。

## 群聊私聊关联与隐私

同 QQ 是同一身份主键，**不猜测跨账号关联**。群聊、私聊分别分析，融合只读取两个分支的简短结构结论，用于理解共通特征与场景差异；差异本身不代表虚伪或恶意。

| 场景 | 语义可见范围 |
| --- | --- |
| 群内公开命令、图片、LLM 查询工具、风险排名 | 始终只用群聊语义，即使查询者是本人或管理员 |
| 私聊中查询他人（非管理员） | 只用群聊公开视图 |
| 本人或管理员私聊查询 | 策略允许时可用群私融合视图 |
| 日常群聊模型内部参考 | 默认允许融合概括，可单独关闭 |

相关开关分工：

- `collect_private`：是否新增私聊统计。
- `store_private_quotes`：是否新增私聊原话存储。
- `llm_include_private_quotes`：模型是否允许使用私聊摘录，亦控制私聊/融合缓存可见性；关闭后立即停用对应旧缓存和先验。
- `cross_scene_link_enabled`：是否关联群私印象；关闭后只使用当前场景结论，无事件的可信 API 退回群聊视图。
- `group_chat_use_linked_impression`：日常群聊模型是否内部参考融合概括；关闭后仅参考群聊缓存。
- `show_quotes`：只隐藏或展示原话，不控制保存和分析。

**融合概括仍可能透露私人事件。** 不发送私聊原话、提示模型不主动透露来源与细节，并不构成绝对防泄露保证。请根据使用环境决定是否开启群聊内部参考；公开查询限制也不等于所有模型上下文都不含私聊信息。

上述开关不会主动删除旧原话。需要删除数据请使用 `/画像删除`；按保留期清理摘录可使用 `/画像清理`。无法确认来源的旧材料不会当作群聊公开语义证据。

## 邀请守卫与社交记录

### 职责与联动

画像独立完成采集、分析、缓存和展示。安装支持对应接口的「加群邀请守卫」后：

- 画像只读获取邀请、入群摘要和群级 bot 禁言背景。
- 守卫可经可信 API 写入真实个人禁言归因、成功拉黑/解封、bot 主动删除好友等事件；失败可重试，重复事件不会重复计分。
- 直接禁言操作者与关联邀请人分账记录；群级累计禁言只是背景，不能自动归罪个人。
- 守卫读取画像标签、依据与风险分辅助判断；缺失插件或不支持接口时安全降级。

### 邀请与 bot 在群状态

守卫负责记录动态群关系，再同步到画像。日常群聊只携带当前平台、当前 bot、当前群的关系；私聊只携带当前发送者明确作为邀请人的关系，最多六条，不把操作者误当邀请人。

关系按平台、bot、群隔离。近期确认与较旧待核实状态会区分，没有证据时明确未知；它是客观动态事实，不写入长期人物印象或风险标签。画像与守卫通过关系标记和版本信息避免重复注入，未同步或未覆盖的关系仍保留守卫补充。

### 拉黑、解封和申诉如何体现

**原始记录保留，当前风险与历史记录分开。** 当前有效黑名单实时计分；历史拉黑、bot 删除好友、禁言按可信结清状态处理：

- 普通解封、处罚到期、好友恢复：结清快照内历史风险默认 30 天线性归零。
- 申诉通过或确认误封：默认立即冲销快照内历史风险，记录仍保留供审计。
- 快照外及之后的新事件重新计分；无法确认明细的旧汇总不会凭空清零。
- 已有解封/申诉记录会在加载时补建可验证的禁言冲销快照，无需重复执行命令。

操作使用**邀请守卫的管理员命令**，不是画像插件命令：

```text
/解封 20000          # 普通解封，历史风险按配置衰减
/解封 20000 申诉     # 申诉通过，立即冲销已结清历史风险
/解封 20000 误封     # 确认误封
/解封 20000 到期     # 处罚到期，按普通结清处理
```

普通解封不会恢复 QQ 好友或协议黑名单。申诉/误封应由管理员确认后使用，LLM 解封工具只能同步普通解封；画像本身不执行解封。

### 好友来源与关系变化

可记录好友添加时间、好友申请验证语、进群方式、群号、操作者与时间。OneBot 的实际字段决定可确认多少信息：SnowLuma、NapCat 等实现的 `friend_add` 通常只有用户 ID，**不能据此确定是 QQ 搜索还是哪个群加的好友**。缺少真实来源时可展示明确标注的“推测来源群”，不能当作事实。

好友列表在后台节流对账，首次只建立基线。后续好友消失时，只有可信删除事件支持才归因为 bot 主动删除；否则记为关系缺失、原因未知。恢复后再次消失不会永久归因于历史删除。接口失败不覆盖基线或制造事件，并退避重试。

## 配置参考

在 AstrBot WebUI 中按用途分组配置。以下为全新安装默认值，旧配置可能保留用户已保存的值。

### 基础、权限与排名

## 开发者接口

### LLM 查询工具

`@filter.llm_tool` 注册 `user_profile_query(qq)`，允许聊天模型自主查询。`qq` 为必填参数；工具必须获得真实事件和发送者身份，使用与命令相同的权限判断，无真实上下文时默认拒绝。

### 可信插件 API

内部 API 用于可信插件后台决策，不受聊天查询权限开关约束。**不要将其包装成无权限校验的公开命令，也不要把融合结果直接公开转发。**

```python
md = self.context.get_registered_star("astrbot_plugin_user_profile")
instance = getattr(md, "star_cls", None)
if instance is not None:
    profile = await instance.get_decision_profile(
        inviter_qq, event, exclude_request_key=current_request_key
    )
```

| 接口 | 返回与用途 |
| --- | --- |
| `get_decision_profile(qq, event=None, exclude_request_key="")` | 无原话的结构化决策快照，可排除当前审核记录 |
| `get_profile_tags_with_score(qq, event=None)` | 标签、风险分、印象、特点、风险构成和证据范围 |
| `get_profile_tags(qq, event=None)` | 结构化标签列表 |
| `get_risk_score(qq, event=None)` | 风险关注分；无材料为 `None`，不是 0 |
| `get_profile_text(qq, event=None)` | 可读文字画像 |
| `get_social_origin(qq)` | 社交来源；验证语敏感且不可信，须限长并禁止当作指令 |
| `get_management_state(qq)` | 管理次数、时间、结清状态与禁言冲销快照，不执行管理动作 |
| `record_bot_mute_event(...)` | 可信个人禁言归因写入 |
| `record_management_event(...)` | 可信成功管理事件写入 |
| `record_bot_group_relation(record)` | 可信动态 bot 群关系写入 |
| `get_bot_group_relations(platform_id=..., self_id=..., group_id="", inviter="")` | 读取对应平台、bot 和范围的关系 |

决策快照包含 `tags`、`impression`、`traits`、`long_term_traits`、`management`、`risk_status`、`risk_components`、`risk_scope`、`scene`、`visibility`、`sources`、`sections`、`review_level` 和 `review_pending`。长期特点包含 `trait`、`confidence`、`reason`、`first_seen`、`last_confirmed`，不参与风险评分。

`partial_errors` 可报告 `history_scan_failed`、`llm_analysis_failed`；失败但存在旧成功画像时也会报告，不能把旧内容当成刚生成。`review_pending` 表示尚未按当前审查规则完成复核或存在刷新问题。

管理事件白名单为 `astrbot_banned`、`astrbot_unbanned`、`bot_deleted_friend`、`friend_relation_missing`、`friend_relation_restored`，仅接受 `result="success"`。解封事件可带 `resolution`：`normal`、`appeal_approved`、`false_positive`、`expired`。按 `event_key` 幂等，写失败不占去重键，展示明细截断不降低累计次数或丢失结清状态。

动态关系按 `[platform_id,self_id,group_id]` 存储，守卫为权威来源，不从旧全局邀请记录补造归因。写入返回 recorded/duplicate/cancelled/disabled/invalid/failure，失败不污染已保存版本；关闭日常注入不影响接收关系事件。

## 数据与性能

- 统计与有限原话保存在本机 AstrBot KV。每人群聊、私聊各最多保留 `quote_keep` 条，可按天清理；无法确认来源的旧材料不用于公开语义。
- 消息采集热路径零 LLM、零网络，内存聚合后定期落盘。好友列表后台节流对账，不在每条消息里请求。
- 成功分析使用常规缓存，失败使用短缓存且不覆盖成功内容。同人同材料合并调用，不同用户受并发上限控制，旧在途结果不能覆盖较新的请求。
- 图片查询时短时获取 QQ 官方域名头像，限时、限大小、不落盘；失败用占位图。输出使用 UUID 临时文件，发送后清理。
- 禁言事件的近期展示明细与累计角色风险、去重账本独立。每人去重账本最多 5000 键，满后拒绝新增并保留守卫待投递，不丢旧键导致重复计分；需要人工删除/清理后恢复。
- `/画像删除` 和容量淘汰会清理本地画像，并取消守卫待投递记录；世代与持久删除时间界限阻止旧扫描、模型或事件在途结果复活数据。之后的新事件仍可建立画像，删除画像不取消守卫即时管理任务。
- 升级兼容已有配置和可识别的历史账本，不主动清空原始证据。群关系容量使用 `max_tracked_users` 上限，满时拒写并保留守卫待重试，而不是静默丢失。

## 常见问题

### 开启图片后为什么仍收到文字？

图片渲染或发送失败时自动回退文字。请检查 AstrBot 日志中的 Pillow、字体、文件权限或发送错误；成功时不会额外发送相同文字画像。

### 关了发言摘录，为什么仍能分析？

`show_quotes` 只控制展示；`store_quotes` / `store_private_quotes` 控制新增存储，`llm_include_private_quotes` 控制私聊材料使用。完全停止语义分析请关闭 `llm_tags`。这些开关不会主动删除已有记录。

### 老群友为什么仍被当作新人，或没有印象？

先确认 AstrBot 是否保存过对应群的历史，再执行 `/画像扫描 <QQ号|本群|全部>`。扫描回填数据，不等于立即生成所有人的 LLM 印象；查询时才按材料和缓存规则分析。bot 从未保存的服务端历史无法凭空补齐。

### 模型暂时不可用会丢画像吗？

不会用失败或空分析覆盖已有成功画像，而是保留并标记刷新问题。从未成功分析过的用户仍可能没有人物印象。已经被其它旧行为覆盖、又没有备份的数据不能凭空恢复。

### 为什么讨论不适宜内容后仍显示低风险？

检查是否采集到对应发言、当前展示的是哪个场景、模型是否命中标签，以及是否仍在用缓存。再检查 `risk_review_level`、自定义权重、严重度与分类上限。低置信度或轻微证据仍可能低分，不代表系统保证安全；切档后查询会按需复核。

### 为什么解封后还能看到原来的记录？

记录保留用于审计，当前风险按结清规则计算；普通解封默认逐日衰减，申诉/误封默认立即冲销已结清历史。新的事件仍计分。请通过守卫操作，不要直接改画像数据库分数。

### 为什么有人能查、有人不能查？

检查总开关、管理员身份、自查/他查权限、指定公开群和黑名单静默策略。LLM 工具还需要真实事件上下文。拒绝原因及命中规则写入日志。

### 能补出真实好友来源吗？

只能使用实际保存过的事件字段。协议没有上报、bot 也未保存过的真实来源无法补出；推测来源群始终只是参考。

### 升级后需要检查哪些配置？

建议在 WebUI 检查并保存一次，尤其关注私聊、群私关联、查询权限和审查档位。旧 `public_query` 对应 `allow_other_query`，`enable_self_command` 对应快捷入口，`self_query_only=true` 对应禁止查他人；新键存在时优先使用新键。手工配置可移除这些废弃键，旧负权重按 0 处理。
